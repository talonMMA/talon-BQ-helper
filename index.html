DoorDash — Code Craft Technical Interview

开场 · Self-Intro（工程师版, ~50 秒）

Quick intro — I've spent the last four years as a Software Engineer at Google, on the High Accuracy Location team. We provide high-precision positioning to Google's business clients — so Street View runs on it, Waymo's robotaxis run on it, Wing's delivery drones run on it.

As for my own work — it comes down to a few things. First, implementation: I've taken theory that lived only in research papers — formulas, math — and built it into our positioning engine, the thing that actually delivers that accuracy. Second, I maintain the petabyte-scale data pipeline that feeds that engine its correction data. Third, I designed and still run our large-scale validation system — it blocks bad releases before they reach a client, and it's become our feedback flywheel: it's what lets us ship fast with AI and still trust every release. And on top of that, I build tools that speed the whole team up — and lately I've started taking research to production on my own.

Then outside of Google, I've got a part-time project funded by Hong Kong Polytechnic University — a fleet-monitoring and AI-diagnosis system for a vehicle repair workshop. I built the whole thing from zero — frontend, backend, and the AI agent at the core — and it's live in the workshop now. Technicians diagnose and document a vehicle in a fraction of the time, and it even caught a vacuum leak before the failure showed up.

One more thing — I read a lot of technical papers and engineering blogs, partly to track where the industry is going, partly just because I enjoy it. Lately it's been all about running AI agents in production at scale — and two posts from DoorDash's own engineering blog stood out: one on the simulation-and-evaluation flywheel behind your support chatbot, and one on the multi-agent system that cleans up stale feature flags. They stuck with me because they match my own conviction: today's models are plenty powerful — the real secret to production AI is the guardrails: letting the model run as hard as possible while staying reliably inside the lines. Your team's writing has genuinely shaped my thinking.

That's me — happy to dive in.

Optimization — Runtime & Memory (120×, 20×, 75%)

主题：通过多轮系统性优化——架构重构(120×)、查询策略(20×)、内存治理(75%↓)——将定位系统从prototype推向production，交付给Waymo、Maps、Wing
Google (Bluewave RTK)

Situation:

  • High-precision geolocation system
  • System was functionally correct as a prototype, but not production-ready
  • Runtime, memory, and auxiliary workflow performance all far below production bar
  • Internal partners (Waymo, Maps, Wing) needed a production-quality system

Task:

  • Lead performance optimization across multiple dimensions to bring the system to production readiness
  • Output must remain bit-for-bit identical — zero tolerance for any change in positioning results

Action:

  • Runtime — Architecture Refactor (40×): 80% runtime was matrix computation → analyzed and drastically reduced matrix dimensions without affecting output → 40× speedup alone
  • Runtime — DB Query Optimization (3× → total 120×): optimized query strategy to avoid hitting unnecessary shards → additional 3×, bringing total to 120×
  • Auxiliary — Parallel Processing (20×): analytics tool wasn't the main bottleneck, but noticed it could be parallelized → 20× speedup; prevented it from becoming a bottleneck when later processing Waymo's large-scale datasets
  • Memory — Customer-Driven (75%): StreetView team's customer reported OOM on large datasets — proactively optimized system architecture, removed unnecessary heavy allocations → 75% reduction, allowing customers to run in smaller containers
  • Each optimization validated end-to-end — output bit-for-bit identical
  • Shared profiling methodology with team → adopted for other components

Result:

  • Main pipeline: 120× faster (40× architecture + 3× DB)
  • Auxiliary workflows: 20× faster, prevented future bottleneck at Waymo scale
  • Memory: 75% reduction, unblocked StreetView customer, saved compute resources
  • Combined: system went from prototype to production — delivered to Waymo, Google Maps, Wing

Learned:

  • Production readiness requires optimizing across multiple dimensions, not just the obvious bottleneck
  • Proactive optimization (memory issue) is as valuable as reactive — didn't wait for it to become a blocker for more partners

Backward Processing — P99 Error Fix

主题：主动识别了长期未解决的P99尾部误差问题(20m+)，通过设计双向处理算法将P99降至1米以内，成为production标准组件，并直接促使Waymo主动联系替换其开源工具。
Google (Bluewave RTK)

Situation:

  • High-precision geolocation system — P50 accuracy excellent (cm-level), but P99 had extreme failures: 20+ meters
  • Problem existed long-term, no one had systematically addressed it
  • Identified this as a critical gap and took ownership proactively
  • Core value of system is precision — P99 at 20m is unacceptable for production partners

Task:

  • Find root cause of P99 long-tail failures and design a generalizable solution
  • Cannot degrade P50/P90 accuracy in the process

Action:

  • Phase 1 — Diagnosis: Visualized all extreme-error cases on map (not aggregated metrics) → failures clustered around obstructed-signal areas (overpasses, urban canyons). Deeper analysis: root cause wasn't the obstruction itself, but corrupted state propagating forward through subsequent time steps.
  • Phase 2 — First Solution + Trade-off: Designed detection + mode switch: when signal quality drops significantly, switch from stateful tracking mode to stateless single-shot mode. Fixed most extreme cases, but introduced risk: false triggers would unnecessarily drop accuracy.
  • Phase 3 — Backward Processing (core innovation): Insight: forward-only processing forces a hard choice. Designed bidirectional processing: run forward pass, then backward pass, fuse both results. Backward pass uses later clean data to refine earlier uncertain moments → eliminates the trade-off.
  • End-to-end validation: P99 error from 20+ meters down to sub-1 meter
  • Backward processing integrated as standard component in production pipeline

Result:

  • P99: 20+ meters → sub-1 meter
  • Backward processing became standard production component
  • Waymo proactively reached out to replace the industry-standard open-source baseline with our system
  • Directly drove customer expansion for the product

Learned:

  • Surface symptom (overpass failures) and root cause (error propagation) can be completely different
  • When a forward-only approach has a fundamental trade-off, rethinking information flow direction itself can break the constraint

AI Agent Skill — Golden Test Automation

主题：在20%时间里利用Agent Skills将团队高频痛点（golden test更新，每次30分钟+）自动化为一句话触发的智能工作流，解决了之前Python脚本无法自适应、难以被记住的根本缺陷，成为团队标准工具。
Google (Bluewave RTK)

Situation:

  • The positioning system has a golden test: before each commit, runs the full pipeline on real data — any precision change beyond 1nm triggers failure
  • As customers grew (Waymo, Wing, StreetView), test cases kept expanding — golden file updates became a high-frequency pain point
  • Triggered multiple times per week, hit almost every team member — 30+ min of repetitive manual work each time
  • Previous Python script had two fundamental flaws: couldn't auto-adapt to newly added test cases; team members kept forgetting it existed

Task:

  • Fully eliminate the golden file update inefficiency
  • Solution must be easy for everyone on the team — no dependency on "remembering the script name"

Action:

  • Google internally launched new AI Agent (Gemini Coder) supporting Agent Skills — evaluated during 20% time
  • Why Agent Skill beats a script: natural language invocation → solves "can't find/remember" problem; LLM handles cases the script can't cover → solves "can't auto-adapt" problem
  • Built a dedicated SKILL: one sentence to trigger → auto-runs script to update all golden files → auto-runs tests to verify → if new test cases detected, auto-upgrades script to adapt
  • Completed from idea to working tool within 20% time
  • Demoed to team at daily meeting

Result:

  • 30+ min manual work → one sentence, Agent handles everything in background
  • Became team's standard workflow
  • Solved both fundamental flaws of the previous Python script
  • Some team members started building their own Agent Skills for other workflows

Learned:

  • When facing new tech concepts, the key isn't learning the concept itself — it's quickly identifying which real problem it can solve
  • Good tooling isn't just technically functional — it must have zero adoption barrier

Satpvt Service Bugfix — Legacy System Recovery

主题：主动接手前人离职后无人维护的卫星定位关键服务，在零背景下诊断出v3/v4数据格式不兼容问题，通过"零修正优于错误修正"的判断快速恢复生产，随后完成完整升级将精度从10m提升至±2m。
Google (Bluewave RTK)

Situation:

  • Upstream signal-correction service — critical input to the positioning pipeline
  • Original owner left months earlier, work completely stalled, no one had context
  • Service was silently producing ~10m errors, causing downstream positioning pipeline to fail
  • Proactively took ownership with zero prior context

Task:

  • Restore downstream production stability as quickly as possible
  • Then properly fix the root cause

Action:

  • Phase 1 — Diagnosis: No documentation, no handoff — reconstructed system behavior from only two old bug tickets and downstream error reports. Built minimal test setup to reproduce failure. Root cause: data source upgraded from v3 to v4 format, but parser still v3 → silently reading incorrect correction values.
  • Phase 2 — Emergency fix: Full parser upgrade would take weeks but production was blocked. Key judgment: applying wrong corrections was worse than applying no correction at all. Disabled v3 correction logic → system uses 0 as correction value. Not perfect, but strictly less harmful — downstream pipeline immediately unblocked.
  • Phase 3 — Full upgrade: Completed full parser upgrade to v4 standard. Accuracy improved from ~10m to ±2m.

Result:

  • Emergency fix: downstream positioning pipeline unblocked immediately
  • Full upgrade: accuracy from ~10m → ±2m (5× improvement)
  • Inherited abandoned, broken service → restored and upgraded to production quality

Learned:

  • When inheriting legacy systems under pressure, controlled progress beats waiting for perfect understanding
  • The best emergency fix isn't always the most technically correct one — it's the one that causes the least harm while buying time

Technical Conflict — Base Station Threshold

主题：在base station选站阈值决策中，与researcher产生技术分歧（20km vs 50km），通过全面数据分析和客户需求对齐证明20km方案更符合production目标。

  • Directly affects positioning quality for all downstream clients

  • Resolve disagreement with data, not opinion
  • Prove which threshold better serves production clients

Action:

  • Ran controlled experiments across multiple thresholds. 20km: P50 ~10cm→~15cm (slightly worse), P95 ~60cm→~50cm (meaningfully better).
  • Aligned with client requirements: Waymo and StreetView consistently cared more about worst-case accuracy. Lane-level requirement tolerates up to ~50cm — P50 difference irrelevant, but P95 difference is meet vs. fail.

Learned:

  • Technical disagreements best resolved by reframing to client requirements
  • Data without context doesn't settle debates — data aligned to real requirements does

V2 Agent Harness Pivot — Context → Harness Engineering

主题：识别V1固定pipeline的根本局限——LLM没有任何主动权——将平台从"上下文工程"重新设计为"harness工程"，在36小时sprint内端到端构建了自主诊断agent harness。

  • Built V1 of the AI diagnostic platform as a fixed deterministic pipeline: rule-based preprocessing → anomaly detection → clue generation → RAG → single-shot LLM
  • Recognized a fundamental limitation: the LLM had no agency over data selection, retrieval, or follow-up investigation — the platform was a sophisticated QA bot, not a diagnostic agent
  • Could not refine its own queries, could not iterate, could not say "I need more data on a specific telemetry signal"

  • Sole architect and engineer — needed to research, design, propose, and ship

  • Researched Anthropic's harness engineering principles and production agent design patterns

  • Extended in follow-up work: agent-native tool redesign (replacing thin V1 wrappers), multimodal tool results (visual evidence from manuals)

  • Platform evolved into an autonomous diagnostic agent that reasons iteratively, selects tools dynamically, and decides when it has sufficient evidence
  • V2 harness became the foundation for all subsequent agent work (structured manual navigation, LLM-as-judge eval framework)

Learned:

  • A focused sprint with a clear architectural blueprint beats months of incremental drift
  • Build the runtime first, then redesign the tool surface around what the agent actually needs — rather than wrapping legacy code

LLM-as-Judge Evaluation Framework

主题：设计并构建了一套LLM-as-judge评估框架，把对agent的"感觉好像变好了"换成可重复、可对比的量化基准——以iteration为单位推进agent质量。
PolyU (STF AI Diagnostic Platform)

Situation:

  • After shipping the V2 agent harness and structured manual navigation, iteration on agent quality was running on gut feel — every change might help or hurt, but there was no measurement
  • Without a benchmark, every "improvement" was an opinion; regression risk grew with each change
  • Needed eval infrastructure that scales to multiple manuals and survives ongoing prompt and tool changes

Task:

  • Establish a durable benchmark to iterate on agent quality with metric-driven feedback
  • Solve the methodological challenges: who judges? how to avoid evaluation circularity? how to prevent silent regressions?

Action:

  • Designed a cross-model framework — different model for golden-set generation vs. judging — eliminating same-model self-grading circularity
  • Built a restricted manual-search sub-agent with explicit tool-scope constraints so the sub-agent reasons strictly within its assigned scope, enabling clean fact-recall scoring
  • Designed a multi-dimension grading rubric: section match, fact recall, hallucination guard, citation correctness, tool-trajectory shape — with deterministic judge settings and a pinned model identifier so scores stay comparable across runs
  • Built a grounded golden-set generator and human review CLI for workshop-expert validation: every candidate verifies its quote verbatim against source before writing — failures dropped, never written
  • Adopted an immutable-version policy for golden sets: corrections bump to a new version directory rather than editing in place, so historical scores remain reproducible
  • Captured a baseline benchmark on a real Chinese-language service manual, identified reproducible failure patterns, and ranked next iteration steps by expected impact and cost

Result:

  • The eval suite is now the regression-tracking foundation for all future agent and prompt changes — every change has a measurable before/after
  • Identified four reproducible failure patterns and two judge-model anomalies, giving a prioritized roadmap rather than guesswork
  • Cross-model + immutable-version design means scores stay meaningful as the platform evolves

Learned:

  • An AI system without an eval framework is unverifiable — building the eval is part of building the system
  • Cross-model design and immutable golden sets are the methodological choices that make scores comparable over time; everything else is implementation
  • Eval-driven iteration changes how you debug: "the score dropped on dimension X for case Y" replaces "the agent seems worse"

Optimizer-as-Fuzzer Pivot — From Tuning Tool to Auto-Bug-Fix Pipeline

主题：主动构建黑盒优化工具替代手工调参；过程中意外发现优化器在corner-case探索中触发了大量难以复现的隐藏bug，顺势在其之上再叠一层"发现→复现→profile→修复CL→ticket"的全自动pipeline，让两层工具在一个项目里串成体系。
Google (Bluewave RTK)

Situation:

  • The positioning engine exposes hundreds-to-thousands of tunable knobs across signal processing, filtering, and motion modeling
  • Researchers and engineers tuned by hand — no systematic way to find non-obvious optima or quantify multi-objective tradeoffs (latency vs fix-rate vs accuracy)
  • I had proposed building a proper tuning tool weeks earlier; no one was assigned

Task:

  • Build an automated parameter-tuning tool on top of Google's internal black-box optimization service that anyone could run with near-zero setup
  • Generalize across arbitrary parameter sets and objectives so the tool stays useful as new algorithms and parameters land

Action:

  • Designed a config-driven workflow with a 3-step UX (edit config → one command → monitor link), so non-experts could drive hundreds-of-parameter studies without learning the optimizer
  • Built in resumability and natural-language config generation via the internal AI coding agent
  • Validated on a real study that quantified the long-standing latency-vs-fix-rate tradeoff the team had carried for months

Pivot — Optimizer-as-Fuzzer:

  • During a 9-parameter study, the optimizer hit corner-case combinations no human would try and triggered multiple engine crashes within ~30 minutes — bugs the team had previously considered very difficult to reproduce
  • Recognized the optimizer was inadvertently acting as a fuzzer (an automated bug finder driven by unusual input combinations) — a discovery surface, not a side effect
  • Built a second pipeline on top: automatic bug discovery → reproduction harness → root-cause profiling → candidate fix-PR generation → bug ticket; humans only in PR review

Result:

  • Tuning tool released team-wide; future-proof — new engine parameters become tunable automatically with no tool changes
  • Auto-bug pipeline has already produced real bug tickets and fix PRs for a class of bugs that previously had no reliable repro path
  • Established a new team pattern: large-scale automated parameter search isn't just for tuning — it's the cheapest fuzzer we have

Learned:

  • The most valuable feature was the one I didn't plan — the optimizer's exploration was a discovery surface; the bug-fix pipeline only became obvious after seeing which corner cases the search actually touched
  • Adjacent automation compounds — Tool A (tuner) made Tool B (auto bug-fix pipeline) a one-step idea instead of a ten-step proposal
  • Broad-applicability tooling is its own research strategy — it surfaces problems the team didn't know to ask about

Ionosphere Paper — Paper-to-Production via AI Orchestration

主题：在自己看不懂论文的前提下，用AI编程agent + 自建评测套件 + 自动调参的工作流，一周独立完成原本需researcher+engineer数周协作的工作；把一篇未实践的学术论文推到生产，让定位引擎有效距离从20km延展到50km，北美覆盖40%→100%，零基建支出避免每年数百万美元订阅扩张开销。
Google (Bluewave RTK)

Situation:

  • Production satellite positioning engine, industry-leading at ≤20km from a reference station; accuracy degrades beyond that range
  • The team's existing third-party reference-station subscriptions covered only ~40% of North America at 20km radius; closing the rest would have cost millions/year — needed an algorithmic fix, not an infrastructure buy
  • Long-standing pain point, no one was assigned

Task:

  • Algorithmic fix to recover long-distance accuracy with zero infrastructure spend
  • Deliver without the traditional researcher → engineer → QA chain the team didn't have bandwidth for

Action:

  • Found a candidate technique. Surveyed the literature; identified a paper proposing to extend the engine's core estimator with an extra variable modeling upper-atmosphere signal distortion — never implemented in any production system I could find
  • De-risked the premise cheaply. A 30-min walkthrough with our research scientist confirmed the math was sound — cheap insurance against building on a flawed premise
  • Designed the workflow, not the code. I couldn't read the paper, so I designed around that:
    • Handed paper + integration objectives to Google's internal AI coding agent; it produced the algorithm changes, no line-by-line review by design
    • Verified via metric movement on an evaluation harness I'd built earlier — thousands of recorded sessions with ground-truth positions
    • Tuned new parameters with my auto-tuner; verified the optimum still held on a separate dataset
  • Team lead pushed it toward production rollout

Result:

  • 40% → 100% effective North America coverage — the 50km accuracy lift matched the prior 20km baseline, so existing subscriptions blanketed the territory. Zero infrastructure spend, millions/year saved
  • +10% accuracy in the 20–50km regime — the technical win that unlocked the coverage jump
  • One person, one week vs. the traditional researcher-+-engineer-+-QA multi-week chain
  • Paper went from "interesting but unvalidated" to shipping in the production engine deployed at Waymo and Street View

Learned:

  • AI orchestration changes the qualifications equation. I couldn't read the paper. With a strong eval harness and a codebase-aware AI agent, being able to read it wasn't required — being able to verify outcomes was
  • Prior infrastructure investments compound nonlinearly. The eval suite (Story 6) and auto-tuner (Story 15) were built earlier for unrelated reasons. AI-multiplied engineers are bottlenecked by verification infrastructure, not code-gen speed
